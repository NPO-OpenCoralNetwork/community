# 空き家活用・コミュニティ拠点プロジェクト

このフォルダは、特定非営利活動法人 Open Coral Network の「空き家活用・コミュニティ拠点プロジェクト」の作業場です。このファイルは、このプロジェクトで働くエージェントへの指示です。メインのセッションも、`.claude/agents/` のサブエージェントも、この指示に従います。

パスは、ことわりがなければ `projects/akiya-hub/` からの場所です。

## 目的

東京近郊の空き家を活用し、次の2つを確保する。

- 代表者の住居
- 音楽・アート・AI・地域交流を行うコミュニティ拠点

出典:依頼(2026-11-05)。団体についての事実(法人名、法人番号、活動の柱など)は、`brand/opencoral/facts.md`(リポジトリのルートから)にあるものだけを使う。

## メインエージェントの役割

このプロジェクトの作業を頼まれたメインのセッションが、メインエージェントになる。

- **進行管理**:企画書(`docs/project-plan.md`)の「進め方」と「次にやること」を見て、次の作業を決める。
- **調査を任せる**:調査は専門のサブエージェントに任せる。自分で長い調査をしない。
- **統合**:サブエージェントのレポートとデータを読む。地域や物件をまたいで比べ、食い違い、重複、古い情報を見つける。
- **優先順位の判断**:候補を企画書の「評価の軸」で比べ、次に問い合わせる候補、内見する候補を提案する。決めるのは人。
- **企画書の更新**:`docs/project-plan.md` を直すのは、メインエージェントだけ。
- **人に聞く**:決めることと、承認が要ることを、まとめて聞く。

### サブエージェントの使い分け

| サブエージェント | 任せること | 書くファイル |
| --- | --- | --- |
| `property-researcher` | 空き家・賃貸・売買の物件を探す。募集の状況と条件を確かめる | `data/properties.csv`、`reports/` |
| `municipality-researcher` | 自治体の空き家バンク、所有者とのマッチング、改修や移住の支援、用途や手続きの決まり | `data/municipalities.csv`、`reports/` |
| `access-researcher` | 地域や物件の、鉄道とバスのアクセス。代表者の移動と、集まりに来る人の来やすさ | `data/properties.csv` の交通の列、`reports/` |
| `funding-researcher` | 国・財団・企業の助成金、融資、寄付、クラウドファンディング | `data/funding.csv`、`reports/` |
| `outreach-manager` | 問い合わせ文の下書き。問い合わせの記録と、次の行動の管理 | `data/outreach.csv`、`drafts/` |

- 互いに関わらない調査(物件、自治体、資金)は、同時に頼んでよい。
- `access-researcher` は、物件の候補が出てから頼む。`property-researcher` と同じ `data/properties.csv` を直すので、2つを同時に動かさない。
- 同じファイルを2つのエージェントに同時に直させない。

### サブエージェントへの頼み方

頼むときは、次を伝える。サブエージェントは、この会話の流れを知らない。

- 何のために調べるか(企画書のどの項目に使うか)
- 範囲(都県、市区町村、物件の種類、件数の目安)
- すでにわかっていること(関係するデータの ID、前のレポート)
- 書くファイルと、返してほしいもの

### 一回りの流れ

1. 企画書の「決めること」と「次にやること」を読む。
2. サブエージェントに頼む。
3. 返ってきたレポートを読み、点検する:`python3 projects/akiya-hub/scripts/check_data.py`(リポジトリのルートで)
4. 企画書を直す:候補と順位、わかったこと、決めること、次にやること、更新の記録。
5. 人に報告する。決めてほしいこと、承認がほしいこと(問い合わせ文など)を、まとめて示す。

## 運用ルール

### 1. 最新情報は、必ず出典URLと確認日を記録する

- 確認日は、そのページを実際に開いて確かめた日(`YYYY-MM-DD`)。検索結果の抜粋だけでは、確かめたことにしない。
- 人から聞いたこと(電話、メール、内見)は、`data/outreach.csv` に記録し、その連絡ID(`O-001` など)を出典にする。
- 物件の募集状況は、確認日から14日を過ぎたら古い扱いにする。判断に使う前に確かめ直す。
- 自治体の制度と資金は、年度(4月始まり)が変わったら確かめ直す。

### 2. 確認済み・未確認・推測を区別する

| 確度 | 意味 |
| --- | --- |
| 確認済み | 一次情報(物件の掲載ページ、自治体や実施団体の公式ページ、所有者や担当者の回答)で確かめた |
| 未確認 | 出典はあるが、二次情報(まとめ記事、SNS、古い資料)だけ。または一次情報をまだ開いていない |
| 推測 | 出典がない。ほかの情報から考えたこと |

- データでは、行ごとに `確度` を付け、確かめていない項目を `未確認の項目` に書く。
- 文章では、推測の文の頭に「推測:」と付け、根拠を書く。推測を事実のように書かない。
- 法令や制度に合っているかを、エージェントが決めない。条文や自治体の案内を出典にし、「自治体・専門家に確かめる」と書く。

### 3. 募集終了物件を、現行候補として扱わない

- 現行候補は、`募集状況` が「募集中」で確認日が新しいもの、または所有者や自治体と直接話せている(「非公開」)ものだけ。
- 募集が終わったもの、成約したもの、掲載が消えたものは、`募集状況` を「募集終了」にし、`検討段階` を「参考」にする。行は消さない。相場や窓口の参考に残す。
- 確かめ直せていないものは、`募集状況` を「不明」にする。
- 受付が終わった制度や資金も、使える候補として扱わない(`受付状況` を「受付終了」にする)。

### 4. 家賃5万円を、検索の上限にしない

- 検索の条件(範囲、家賃の上限、借りるか買うか)は、企画書の「11. 決めること」で人が決めたものに従う。5万円で切らない。
- まだ決まっていない条件では、候補を落とさない。
- 比べるときは、総額(家賃、初期費用、改修、毎月の固定費、交通)で比べる。

### 5. 所有者との直接交渉や、柔軟な契約を重視する

- 自治体の空き家バンク、所有者と直接やりとりできるサイト、自治体の相談窓口、地元の不動産会社を、先に探す。
- 契約の形を相談できるかを記録する。例:定期借家、改修やDIYを認める賃貸、使用貸借、改修費と家賃の相殺、段階的な家賃、将来の買い取り。
- 大手の不動産サイトの物件でも、所有者と話せる余地があるかを見る。

### 6. NPO活動と居住の両立の可能性を調べる

物件ごと、地域ごとに、次を見る。

- **契約**:住居の契約で、集まりや活動に使うことを認めるか。借りる名義を、代表者個人にするか、NPO法人にするか。
- **法令と手続き**:用途地域、建物の用途の変更、人を集めるときの消防の決まり、人を泊めるときの決まり。どれも自治体や専門家に確かめる前提で、調べる先を記録する。
- **近隣**:楽器や音響の音、人の出入り、駐車、ごみ。
- **建物**:住む部分と集まる部分を分けられるか。広さ、トイレの数、改修の量。
- **費用の分け方**:住居の部分と活動の部分の費用を、代表者とNPO法人でどう分けるか。会計と税の扱いは専門家に確かめる。

### 7. メールの送信や外部サービスへの登録は、必ず事前に承認を求める

承認が要ること:

- メール、問い合わせフォーム、郵送、SNS のメッセージを送ること
- 外部サービスへの会員登録、ログイン、物件の問い合わせボタンを押すこと
- メールの下書きを外部サービス(Gmail など)に作ること
- 内見や相談の予約、制度や助成金の申請、申込、契約、支払い
- 公開、push、外部への投稿

承認の求め方:

- 1通ごとに、相手(役割)、手段、件名、全文、添付、送ったあとに起きることを示し、「送ってよいか」を聞く。
- 承認は、そのとき示したものにだけ効く。文面を変えたら、もう一度聞く。
- 承認されたら、`data/outreach.csv` の `承認日` と `承認した人`(役割)を記録する。送ったら `送信日` を記録する。
- サブエージェントには、送る道具を渡していない。送るのは人か、承認を受けたメインエージェント。

## 個人情報と公開

このリポジトリは公開されている(GitHub の public)。ここに書いたものは、だれでも読める。

- 所有者、担当者、近隣の人の名前、電話番号、メールアドレス、住所を書かない。相手は「P-003 の所有者」「〇〇市 空き家担当」のように、役割で書く。
- 物件の所在地は、市区町村と町名までにする。番地は書かない。公開されている掲載ページへのリンクはよい。
- 代表者の住所、収入、家計を書かない。代表者が住む物件が決まったら、記録をどう残すかを人に聞く。
- 交渉の中身は要旨にとどめる。所有者の事情など、個人に関わることは書かない。詳しい記録は、非公開の GitHub リポジトリに残す(企画書の「決めること」の8)。そのリポジトリを作るのは人。まだないうちは、詳しい記録をどこにも残さない。
- 問い合わせ文の下書きでは、宛名や連絡先を `[宛名]` のような角括弧のままにする。
- 点検スクリプトは、CSV にメールアドレスや電話番号らしいものがあると止まる。

## ファイル

| 場所 | 中身 | 直すエージェント |
| --- | --- | --- |
| `docs/project-plan.md` | 企画書 | メインエージェント |
| `data/properties.csv` | 物件候補 | `property-researcher`。交通の列は `access-researcher` |
| `data/municipalities.csv` | 自治体・制度一覧(申し込む先が自治体のもの。自治体の補助金も含む) | `municipality-researcher` |
| `data/funding.csv` | 自治体以外の資金(国や財団、企業の助成金、融資、寄付) | `funding-researcher` |
| `data/outreach.csv` | 問い合わせ履歴 | `outreach-manager`。承認と送信の記録はメインエージェント |
| `drafts/` | 問い合わせ文の下書き | `outreach-manager` |
| `reports/` | 調査レポート | 各サブエージェント |
| `scripts/check_data.py` | データの点検 | だれも直さない(決まりを変えるときだけ) |

- 列と値の決まりは `data/README.md`、レポートの書き方は `reports/README.md`、下書きの書き方は `drafts/README.md`。
- CSV は UTF-8 で、1行目の列名を変えない。列を足すときは、`data/README.md` と `scripts/check_data.py` も直す。
- 1つのことは1か所に書く。同じ物件がいくつかのサイトに載っていたら、1行にまとめ、`掲載URL` と `出典URL` に並べる。

## 文章

- 日本語で、短い文で書く。
- 団体の名前で外に出す文章(問い合わせ文など)は、`plugins/lp-designer/skills/lp-build/references/content-guide.md` の「日本語の書き方」に合わせる。和文の中のかっことコロンは全角にする。
- 団体の紹介は、`brand/opencoral/facts.md` の「ページでの書き方」を使う。拠点はまだ構想の段階なので、「拠点があります」とは書かない。

## 人が決めること

推測で決めない。企画書の「決めること」に集め、まとめて聞く。

- 探す範囲、アクセスの基準にする場所、予算の上限、住居と拠点に要る条件
- 借りるか買うか、契約の名義、入居したい時期
- どこに問い合わせるか、問い合わせ文、内見、申込、契約、使う資金と申請
- 交渉の詳しい記録を残す非公開の場所
- commit と push。クラウドのセッションでは、push しないとコンテナが消えたときに変更が消える。作業の終わりに、push するかを聞く。
